> 这一课回答三个问题：**JavaScript 到底有什么痛点？TypeScript 凭什么解决它？它适合谁用？**
> 学完你会有信心：TS 不是给代码"添麻烦"，而是给代码"上保险"。

## 一、从一个真实事故讲起

想象这样一个线上场景：

```js
// 用户下单后，后端返回的响应
const res = await fetch('/api/order')
const order = await res.json()

// 前端代码以为 order 一定长这样
console.log(order.user.name)      // 用户昵称
console.log(order.totalPrice.toFixed(2))  // 金额
```

后端某次改版把字段名从 `user.name` 改成了 `user.nickname`，或者把 `totalPrice` 从数字改成了字符串 `"99.00"`……

结果：**浏览器控制台一片红**，用户白屏，等发现问题时已经是上线后的第 3 个小时。

> 🧠 这就是 JavaScript 动态类型的宿命：**错误要等到运行时才暴露**，而且错误发生的位置往往离真正写错的地方十万八千里。

## 二、TypeScript 是什么

一句话：**TypeScript = JavaScript + 静态类型系统**。

- 它是 JavaScript 的**超集**：所有合法的 JS 代码都是合法的 TS 代码
- 它在**编译期（开发期）**做类型检查，把错误**拦在运行之前**
- 它编译后生成**纯净的 JavaScript**，任何浏览器/Node 都能跑

```text
┌─────────────────────────────┐
│        TypeScript 源码       │
│  const name: string = "TS"  │
└─────────────┬───────────────┘
              │ tsc 编译（类型检查 + 类型擦除）
              ▼
┌─────────────────────────────┐
│         JavaScript 源码      │
│  const name = "TS"          │
└─────────────────────────────┘
```

**类型注解（`: string`）在编译时就被擦除了**——运行时零开销。这是 TS 最关键的设计之一。

## 三、TS 到底解决了什么？

| 痛点 | JS 的表现 | TS 的解法 |
| --- | --- | --- |
| 拼写错误 | 运行时才报错 | 写错属性名，编辑器立刻红线 |
| 类型混乱 | `"99" + 1` 得 `"991"` | 编译期直接拦截 |
| 重构困难 | 改函数名要靠"全局搜索" | 编译器帮你找出所有调用点 |
| 空值崩溃 | `xxx.name` 报 Cannot read property | strict 模式下提前报错 |
| 文档缺失 | 函数怎么用全靠猜 | 类型即文档，悬停即见 |

**比喻时间** 🎨

- JS 像**自由市场**：什么都能卖，但买错东西没人提醒你；
- TS 像**签合同**：交易前先核对条款，不合规的一律拦下；
- 类型注解就是**合同条款**，编译器就是**公证处**。

## 四、TS 的"四不承诺"

1. **不会让程序变快**——类型在编译期就擦除了，运行时性能与 JS 一致；
2. **不会替你消灭所有 bug**——类型错误 ≠ 逻辑错误，`1+1=3` 这种错它管不了；
3. **不会阻止你写烂代码**——你可以用 `any` 放弃检查（但强烈不推荐）；
4. **不会自动学会 JS 生态**——第三方库需要类型声明（`.d.ts`，第 14 课讲）。

::: tip
TS 的正确打开方式：**"能推断就不写注解"**。大多数情况下编译器自己就能推出类型，你只需要在"它推不出"或"边界"处显式标注。
:::

## 五、场景演练：给事故代码"上保险"

::: exercise
把开头那段事故代码用 TS 重写，要求：`fetch` 结果有类型、字段写错立刻报错。
:::

::: solution
```ts
interface User { name: string; age: number }
interface Order {
  id: number
  user: User
  totalPrice: number
  status: 'pending' | 'paid' | 'shipped'
}

const res = await fetch('/api/order')
const order = (await res.json()) as Order   // 断言成我们约定的形状

// 现在：字段拼错、类型不对，编译期就报错
console.log(order.user.name)            // ✓
console.log(order.totalPrice.toFixed(2)) // ✓
// console.log(order.user.nickname)     // ❌ 编译报错：属性不存在
// order.status = 'done'                // ❌ 编译报错：不是合法状态
```

后端字段一旦变更，**错误会立刻出现在开发者的编辑器里**，而不是上线后的用户浏览器里。这就是"把错误往左移"（越早发现，修复成本越低）。
:::

::: interview
**Q1：为什么说 TS 是 JS 的超集？**
A：任何合法的 JS 代码都是合法的 TS 代码，TS 在语法上兼容 JS，并在其上加了一层类型系统。所以可以把 JS 文件直接改名成 .ts 逐步迁移。

**Q2：TS 会不会拖慢性能？**
A：运行时不会。类型在编译期被擦除，最终产物是标准 JS。唯一代价是编译和开发时的类型检查时间。

**Q3：类型检查能替代单元测试吗？**
A：不能。类型检查解决"值是否符合约定形状"的问题，单测解决"逻辑是否正确"的问题，两者互补。
:::

## 📌 小结

- TS 是 JS 的超集，核心是**编译期静态类型检查**
- 类型注解编译后被**擦除**，运行时零开销
- 最大价值：**把运行时错误提前到开发期**，配合编辑器获得顶级开发体验
- 它不替代测试、不提升运行速度、不阻止你写烂代码——但它能让烂代码**显形**
